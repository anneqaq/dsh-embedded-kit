# 嵌入式固件架构原则

## 一、先定依赖方向：分层是为了"能单独理解一层"

```
         应用逻辑 (app)
              ↓ 只向下依赖
      服务/中间件 (fsm, comm, storage)
              ↓
        驱动/抽象 (drv_uart, drv_flash)
              ↓
         硬件寄存器 / HAL
```

**铁律**：
- **依赖只能向下**。上层可以调下层，下层**绝不能**反过来调上层 —— 包括"回调"这种形式，
  除非回调是由上层注册进下层的函数指针（那是上层的意图，不是下层的依赖）。
- **驱动层不认识业务**。`drv_uart` 只知道"发字节、收字节"，不知道"这条报文是查询电量"。
  一旦驱动里出现业务判断，这层就锁死了，换协议/换业务时全得改。
- **判据**：能不能只把某一层拿出来单独编译、单独测试？不能，就说明层间耦合过头了。

## 二、模块边界：用接口而不是全局变量

- **每个模块一个 `.c` + 一个 `.h`**，`.h` 只暴露必要的接口，内部函数与变量用 `static` 收敛。
- **禁止跨模块直接读写别的模块的全局变量**。要改别人的状态，走它提供的接口 ——
  这样"谁改了这个值"永远只有一处，排查时有明确入口。
- **接口要窄**：一个模块导出十几个函数通常说明职责不清。先问"它到底负责什么"。
- **不要为了"通用"提前抽象**：只支持一种外设的产品里引入驱动注册框架、函数指针表、虚函数，
  换来的是纯开销（Flash 与复杂度）而没有收益。**等你真的有两个实现再抽象。**

## 三、状态归属：一个状态只有一个写者

这是嵌入式里最能减少"灵异 bug"的一条。

- **每个状态变量有且只有一个模块有权写它**，其他模块只能读或通过接口请求修改。
- **ISR 与主循环之间**：ISR 只**投递事件/写环形缓冲**，状态由主循环改。
  （ISR 直接改状态机状态 = 与主循环竞态，且极难复现。）
- **状态机**：状态显式、集中、可枚举（见 `scheduling-patterns`）。
  用一堆 `bool` 拼出的隐式状态是最常见的技术债。
- **共享数据的并发**：单生产者/单消费者环形缓冲可以免锁；其他情况必须用临界区。
  `volatile` 只保证可见性，**不保证原子性**。

## 四、错误传播：明确每一层的失败语义

三层结构下，错误怎么走要在架构上定清楚：

| 层次 | 遇到错误时的责任 |
|---|---|
| 驱动层 | **如实上报**（返回错误码，分清超时/CRC 错/总线故障），**不做业务决策** |
| 服务层 | 按策略处理：重试（有限次）、降级、或上报；把"已重试 N 次仍失败"作为一个明确状态 |
| 应用层 | 决定用户体验：进安全态、提示、重启外设、或停机 |

要点：
- **每一层都要有明确的失败行为**。"假设不会失败"是最贵的假设。
- **错误要能区分**：超时 / 校验错 / 无响应 / 总线故障必须**分开计数**。
  合并成一个"错误标志"会让现场完全无法定位。
- **不要吞掉错误**：可以忽略，但要在代码里**显式写出为什么可以忽略**（如 `(void)ret; /* 非关键日志 */`）。
- **可恢复与不可恢复要分开**：前者重试或降级，后者进安全态并记录。

## 五、配置：编译期还是运行期

| 方式 | 适用 | 注意 |
|---|---|---|
| 编译期宏 / `#define` | 硬件相关、不会变的（引脚、器件型号） | 换硬件要重编，但**能编译期检查**，把错误挡在编译阶段 |
| 运行期配置（NVM 保存） | 现场可调、用户可改的（阈值、通讯地址） | 必须带默认值 + 校验 + 版本迁移（见 `nvm-storage`） |

- **不要把硬件引脚定义放在运行期配置里**：能编译期发现的问题不要拖到运行期。
- **运行期配置必须有恢复路径**：损坏时回落默认值并写回，不能每次上电都走恢复。
- **优先用编译期断言**：能用 `_Static_assert` / 编译期检查表达的约束，就不要留到运行期。

## 六、可观测性：架构的一部分，不是事后加的

在架构阶段就要给"看不到的东西"留出口：

1. **状态查询接口**：当前状态、各任务进度、错误计数器 —— 只读，随时可查。
2. **分类计数器**：不同错误分别计数（超时/校验/无响应）。
3. **复位与故障现场保存**：复位标志 + PC + CFSR 存到掉电不清的地方（见 `fault-diagnosis`）。
4. **一个空闲 GPIO + 一个空闲串口**留给调试与性能测量。
5. **进度变量**：长流程（升级、擦写、标定）要有进度可读。

**判据**：现场返回的一台设备，在不接调试器的情况下，能不能判断"它卡在哪一步、出过什么错"？
不能，就是可观测性不足。

## 七、为约束设计：嵌入式架构的取舍原则

- **算清资源再定结构**：RAM/Flash 只有几 KB 时，不要照搬通用架构。
  RTOS、动态分配、复杂抽象层都要按资源重新权衡（见 `scheduling-patterns` 的判据表）。
- **确定性优先**：实时路径避免动态分配、避免不定长循环、避免浮点（无 FPU 时）。
- **静态分配优先**：内存池 / 静态数组替代 `malloc`；一旦用了动态分配，就必须为"分配失败"设计行为。
- **可测性**：纯逻辑（协议解析、状态迁移、计算）与硬件访问**分离**，
  前者能脱离硬件单测 —— 这是嵌入式里最容易被忽略却收益最大的一条。
- **十年维护视角**：代码的主要成本在维护，不在首次编写。
  能编译期检查的错误、能自解释的命名、能写进注释的硬件依据，都是在降低未来的成本。

## 八、架构评审清单

1. 依赖方向是否单向？有没有下层反向调用上层？
2. 驱动层里有没有业务判断？
3. 每个状态变量是不是只有一个写者？ISR 有没有直接改状态？
4. 每个可能失败的操作，三层各自的失败行为是否明确？错误是否可区分？
5. 跨模块是否只通过接口通信，没有直接读写别人的全局变量？
6. 硬件定义是否在编译期？运行期配置是否有默认值 + 校验 + 版本迁移？
7. 现场不接调试器时，能否判断卡在哪、出过什么错？
8. 纯逻辑是否与硬件访问分离、能否脱离硬件测试？
9. 抽象是否**已经被两个实现需要**？（只有一个实现时的抽象通常是负担）
10. 资源账算过没有？（RAM/Flash/CPU 占用，用 `fw_size` / `sched_analyze` 量化）
