# LVGL 使用模式与移植要点

## 一、先配缓冲：这一步决定后面所有体验

用 `lvgl_mem` 工具算，别凭感觉。三种配置：

| 配置 | 需要 RAM | 特点 |
|---|---|---|
| **局部缓冲（partial）+ 单缓冲** | 屏宽 × N 行 × 每像素字节 | 资源受限 MCU 的常规做法，最省 RAM |
| 局部缓冲 + 双缓冲 | 上面 ×2 | 驱动支持"一边传一边填"时才有收益 |
| **全屏缓冲（full）** | 整帧 × 缓冲数 | 撕裂最少，但需要一整帧 RAM |

**要点与坑**：
- **局部缓冲的行数**：取屏高的 1/10 左右。太小（如 4 行）会让 LVGL 把一次重绘拆成很多次 flush，
  驱动中断/DMA 启动开销占比飙升 → **表现为刷新变慢，而不是变快**。
- **双缓冲的前提**：驱动必须能在传输缓冲 A 的同时使用缓冲 B，并由 `lv_disp_flush_ready()` 配对通知。
  若驱动是"传完再回调"，双缓冲不会带来收益，只是白占一倍 RAM。
- **每像素字节**：`LV_COLOR_DEPTH` 决定 —— 16 位 2 字节、32 位 4 字节。32 位在 SPI 屏上通常只是浪费带宽。

## 二、刷新集成：两种正确接法

### 2.1 主循环（裸机）—— 推荐给无 RTOS 的工程

```c
for (;;) {
    lv_timer_handler();          /* LVGL 处理动画、事件、重绘 */
    app_task_a();
    app_task_b();
    /* 每轮调用一次即可；不要放在定时器中断里 */
}
```
- **`lv_timer_handler()` 不要放中断里** —— 它会做大量计算与内存分配。
- 它返回"下次需要处理的毫秒数"，可以据此决定主循环节拍，但仍在主循环调用。
- 屏幕刷新由驱动的 flush 回调（通常配 DMA）完成，**不要在里面忙等传输结束**。

### 2.2 RTOS —— 单独一个低优先级任务

```c
void lvgl_task(void *arg)
{
    for (;;) {
        lv_timer_handler();
        vTaskDelay(pdMS_TO_TICKS(5));   /* 5~20 ms 通常够；太短只是白烧 CPU */
    }
}
```
- **LVGL 不是线程安全的**。所有 `lv_*` 调用（除 `lv_tick_inc`）都必须**在同一个任务里**，
  或外部加互斥锁把整个 LVGL 包起来。
- **`lv_tick_inc()` 放在定时器中断里**（它是唯一允许在中断里调用的），或启用 `LV_TICK_CUSTOM`
  让 LVGL 自己去读系统 tick。
- RTOS 下容易踩的坑：任务优先级给太高 → 抢占实时任务；栈给小了 → 界面复杂时栈溢出。
  LVGL 任务栈通常需要 2~4 KB 起步。

## 三、内存

- **`LV_MEM_SIZE` 无法静态计算** —— 取决于运行时创建的对象数、样式与文本长度。
  **用 `lv_mem_monitor()` 读 `max_used` 峰值**，再按 1.3~1.5 倍留余量设定。
  经验起点（非计算值）：简单单屏 8~16 KB、多页面+列表+中文 32~64 KB、复杂仪表盘 100 KB+。
- **能不能用外部 SRAM / PSRAM**：`LV_MEM_ADR` 可以指向外部存储，但会牺牲访问速度（尤其是刷新路径）。
- **碎片**：LVGL 自己的分配器碎片可控性一般。**避免频繁创建/删除对象** ——
  用"提前建好、按需隐藏/显示"替代反复 create/delete。
- **对象数量是内存的主要驱动**：一个屏幕里几百个对象比一张大图片更吃内存。

## 四、体积：中文字库是头号杀手

- **完整中文字库一个字号动辄几百 KB**（GB2312 常用字）。这是 LVGL 工程 Flash 超标的头号原因。
- 对策：
  1. **按需裁剪字符集**（只含界面用到的字）—— 收益最大。
  2. 用内置的小字库（ASCII + 少量汉字）配图标字体。
  3. 多字号只保留实际用到的。
  4. 把字库放到外部 Flash 并按需读（牺牲性能换空间）。
- 图片同理：**用 LVGL 的转换工具压缩**，别直接塞 BMP/JPEG 原始数据。
- 用 `fw_size` 分析体积，看是字库/图片大还是代码大 —— 两者优化手段完全不同。

## 五、常见故障对照

| 现象 | 大概率成因 |
|---|---|
| **花屏 / 颜色错乱** | `LV_COLOR_DEPTH` 与驱动的像素格式不一致；字节序（RGB565 高低字节颠倒）；缓冲地址未对齐 |
| **撕裂** | 单缓冲 + 传输中途被改写；或用了非对齐的局部缓冲区域 |
| **界面卡顿** | 局部缓冲行数太小；`lv_timer_handler` 调用间隔太长；每帧重绘整屏（未用脏区） |
| **内存不足 / 随机断言** | `LV_MEM_SIZE` 太小；对象反复创建销毁造成碎片 |
| **完全黑屏** | 驱动 flush 回调没调 `lv_disp_flush_ready()`；或缓冲区地址/长度给错 |
| **偶发死机** | LVGL 在多任务里被并发调用（内存管理非线程安全）；或 flush 回调里忙等 |
| **刷新慢** | 位深选了 32 位；SPI 时钟低于带宽需求（用 `lvgl_mem` 算需要的等效 SPI 速率）；每帧全屏刷新 |

## 六、移植检查清单

1. `LV_COLOR_DEPTH` 与屏幕驱动实际格式**一致**（别只看例程默认值）。
2. `lv_tick_inc()` 的时间基准**真实准确**（不准 → 动画速度异常、超时判断错）。
3. flush 回调**必须**调 `lv_disp_flush_ready()`，且长度/坐标换算正确。
4. 缓冲**地址对齐**（多数 DMA 要求 4 字节或更多对齐）。
5. 用 `lv_mem_monitor()` **实测**内存峰值，而不是按经验猜。
6. 用 `fw_size` 看字库/图片占了多少 —— 提前发现体积问题。
7. 高频刷新场景用 `lvgl_mem` 核对带宽是否够（尤其 SPI 屏）。
