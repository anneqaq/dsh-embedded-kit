# NVM / 片内 Flash 存储设计

## 一、先认清片内 Flash 的物理约束

| 事实 | 后果 |
|---|---|
| **擦除单位 ≫ 写入单位**（常见页 1~4 KB，写粒度 1~8 字节） | 改 4 字节要先擦掉整页 → 其余数据必须先备份到 RAM |
| **擦除次数有限**（常见 1 万~10 万次，查数据手册） | 频繁写同一页 → 几个月就写坏 |
| **擦除后位为 1，写只能把 1 变 0** | 想再写回 1 必须擦除；这决定了"只能追加"的日志式写法 |
| **擦除耗时远大于写**（毫秒级） | 擦除期间 CPU 可能停住（取决于是否从同一 bank 取指） |
| **写/擦期间掉电 → 该页数据损坏** | 必须有掉电安全策略，不能指望"写到一半不会掉电" |

**第一条纪律**：把"要保存的参数"按**写入频率**分区。每次都改的计数器和一年改一次的配置，
绝不能放同一页 —— 前者会把后者一起写坏。

## 二、寿命估算：先算清再设计

用 `nvm_layout` 工具算。两种模型的寿命差**几个数量级**，必须按实际写法定：

| 模型 | 行为 | 每天擦除次数 |
|---|---|---|
| `page-rewrite`（整页重写） | 每次保存都擦同一页并重写全部 | = 每天写入次数 |
| `circular-log`（环形日志） | 追加写到空页，写满才擦最旧的页 | = 每天写入页数 ÷ 页数（**均摊**） |

**同样的负载，8 页的环形日志比整页重写耐久约 8 倍。**

降低磨损的常规手段（按性价比排序）：
1. **环形日志 / 双缓冲**替代整页重写（改动最小、收益最大）。
2. **RAM 缓存 + 合并写**：把多次小改动攒起来，触发条件（定时/关机/变更累积）满足才落盘。
3. **降低保存频率**：区分"必须立即持久化"和"可以延后"的字段。
4. **减小每次写入量**。
5. 真的不够就换 **外部 EEPROM / FRAM**（FRAM 擦写次数几乎无上限，且写入速度接近 RAM）。

**不要用别的型号或"经验值"代替数据手册的擦除次数上限** —— 它线性决定寿命，猜错就是几十倍误差。

## 三、掉电安全：三种做法的可靠性阶梯

### 3.1 最弱：单份直接写（**不要用于重要数据**）
```
擦除页 → 写入新数据
```
擦除后、写完前掉电 → **数据全丢**。只能用于可重建的数据（如统计计数）。

### 3.2 进阶：双备份 + 序号（A/B 交替）
```
页 A: [序号 N]   [数据] [CRC]
页 B: [序号 N+1] [数据] [CRC]   ← 新写入的
```
- 写完 B 并校验通过后，才认为 B 有效。读取时**取序号较大且 CRC 正确的一份**。
- 掉电任意时刻，至少有一份完好 → 可靠。
- 注意：**擦除前不要动旧数据**。顺序是"擦另一页 → 写 → 校验 → 更新有效标志"。
- 序号会回绕：用无符号比较，或留一位做"当前有效"标志。

### 3.3 最强：日志式追加（环形块）
```
[块0: 序号0 数据 CRC][块1: 序号1 数据 CRC][块2: 空]...[块N: 空]
```
- 新数据总是追加到第一个空块；块满后擦掉**最旧**的一整块再用。
- 读取时扫描全块，取序号最大且 CRC 正确的。
- 优点：**每次写入不需要擦除**（大部分时候只是把 1 写成 0），磨损天然均摊，寿命最长。
- 代价：需要一个"块头"标记有效性；扫描耗时随块数增长（可缓存索引）。

**通用铁律**：无论用哪种，**每份数据都要带 CRC 和序号/版本**。没有校验就无法判断"这份是好的还是写坏的"；
没有序号就无法判断"哪份更新"。

## 四、数据完整性与版本迁移

- **CRC 覆盖整个数据体**（含长度与版本字段）。长度字段也要校验，防止读到越界长度。
- **留版本号**：固件升级后参数结构会变。读取时：
  - 版本相同 → 直接用
  - 版本较旧 → 迁移（给新字段填默认值），**不要直接丢弃**（用户参数不该因为升级而丢）
  - 版本较新 → 说明是降级运行，按默认值处理并告警
- **默认值要能恢复**：数据损坏时回落到编译期默认值，并**把默认值写回去**（避免每次上电都走恢复路径）。
- **写保护/读保护**：涉及密钥或标定值，考虑启用器件读保护，避免被读出。

## 五、常用分区布局参考

```
[ Bootloader ]  页对齐，通常 8~32 KB，永不被应用改写
[ App        ]  页对齐，升级时整块替换（或 A/B 双区）
[ App 备份/OTA ] 页对齐，与 App 同大小（A/B 双区升级时必需）
[ Config     ]  **至少两页**，双备份或日志式，低频写
[ Log/统计   ]  环形日志，高频写，整块可丢弃
[ 标定/密钥 ]  读保护区，单独一页，极低频写
```

检查项：
- **每个区都对齐到擦除页边界**（否则擦一个区会连带擦掉相邻区的尾部）。
- **留余量**：剩余空间不足一页时，日后加功能会立刻撞墙。
- **Boot 与 App 之间要有明确约定**（跳转地址、有效性标志、版本号），并且**升级过程中掉电要能回退**。
- 分区表**写进文档**，别只存在于某人的脑子里。

## 六、常见故障与成因

| 现象 | 常见成因 |
|---|---|
| 参数偶发丢失 | 单份写入 + 掉电；或没校验 CRC 就采信 |
| 参数变成 0xFF | 擦除后没写入（掉电在中间），且没有备份 |
| 用几个月就写坏 | 整页重写同一页，没有磨损均衡 |
| 改了参数却偶发变回旧值 | 双备份的序号比较逻辑错（回绕处理不当） |
| 升级后参数全丢 | 没有版本迁移逻辑，直接按结构体读 |
| 相邻分区数据被破坏 | 分区未按擦除页对齐 |
| 写入期间程序卡顿/复位 | 擦除耗时长，或擦除与取指在同一 bank 且未做处理 |
