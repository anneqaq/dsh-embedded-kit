# 固件体积优化流程

## 铁律：先量后改，每步复测

**不允许凭感觉优化。** 没有量化数据就开始改编译选项，结果通常是
"改了十项、体积降了 200 字节、还引入了新 bug"。

标准动作：

1. **先拿到量化数据**，按手头有什么选一种输入：

   | 手头的产物 | 说明 | 覆盖的工具链 |
   |---|---|---|
   | **ELF 文件**（首选） | 直接读节区表，最通用、最准 | 几乎所有：GCC 系、Keil AC6、IAR 都能产出 ELF |
   | GNU ld `.map` | 链接时加 `-Wl,-Map=out.map` | GCC 系：arm-none-eabi / riscv / xtensa-esp / avr / msp430、PlatformIO、ESP-IDF、Zephyr、CMake |
   | Keil MDK `.map` | Options → Listing 勾选 Linker Listing | armlink / armlink6 |

   > 判据：**能用 ELF 就用 ELF** —— 节区头是权威源，不经过任何"打印再解析"的中间环节。

2. 拿到 ROM（Flash 镜像）与 RAM 的实际占用、以及**按目标文件/段排序的体积清单**。
3. 记下基线数字。每次只改**一类**东西，改完重新量，记录增量。
4. 任何一次改动如果体积没降反升（很常见：打开 LTO 后某些工程反而变大），
   就回退，不要"反正打开了应该没坏处"。

口径（各家一致）：

- **ROM = Code + RO Data + RW Data**（RW Data 初值要存进 Flash，所以计入 ROM）
- **RAM = RW Data + ZI Data**

两个数必须**分开看**。只看 Flash 优化了、RAM 爆了，是常见翻车方式。

## 一、编译选项层（收益最大，风险最低）

| 手段 | Keil AC6 | GCC | 注意 |
|---|---|---|---|
| 优先体积 | `-Os` | `-Os` | 先确认当前是不是 `-O0`（调试遗留），这一项常有惊喜 |
| 链接时优化 | `-flto` | `-flto` | **必须所有目标文件一起参与**；混合了不同 LTO 设置的库会失败或静默降级。有工程反而变大，要复测 |
| 函数/数据分段 | `-ffunction-sections -fdata-sections` | 同 | 单独用没效果，必须配合链接器的段回收 |
| 段回收 | 链接器 `--remove`（配合分段） | `-Wl,--gc-sections` | 回收未被引用的函数与数据，对"引了现成库只用一个函数"的场景收益大 |
| 精简 C 库 | 勾选 **MicroLIB** | `--specs=nano.specs` | 注意 nano 库与完整库的 `printf` 浮点行为不同 |
| 去 C++ 开销 | `-fno-exceptions -fno-rtti` | 同 | 异常表在 Flash 里占比可观；确认确实没用到 |
| 去展开表 | `-fno-unwind-tables -fno-asynchronous-unwind-tables` | 同 | 会牺牲调试体验，发布版本再开 |
| 调试信息 | `-g0` 或链接时分离 | 分离到独立文件 | **Debug 信息不进 Flash**，但会让 `.map` 看起来很大，别被吓到 |

> 审查提醒：`.map` 里的 `Debug` 列**不算 ROM 占用**。看到"Debug 占了几十 KB"不必慌。
> ELF 同理：未置 `SHF_ALLOC` 的节区（`.debug_*`、符号表、`.comment`）都不进运行时镜像。

### 其他工具链的对应手段（不要照抄 Keil 的名字）

上一张表以 GNU / Keil 为主。换工具链时按**意图**找对应项，而不是找同名选项：

| 意图 | IAR | ESP-IDF（CMake） | 裸 GCC（RISC-V / ARM） |
|---|---|---|---|
| 体积优先 | Project → C/C++ Compiler → Optimization → **Size** | `CONFIG_COMPILER_OPTIMIZATION_SIZE=y`（menuconfig） | `-Os` |
| 段回收 | 链接器默认丢弃未引用段（留意 `--keep` 例外） | `-ffunction-sections -fdata-sections` + `--gc-sections` | 同左 |
| 精简 C 库 | DLIB 配置选 **normal** 而非 full；关 `printf` 浮点格式化 | `CONFIG_NEWLIB_NANO_FORMAT=y` | `--specs=nano.specs` |
| LTO | Project → Linker → **Link-Time Optimization** | `CONFIG_COMPILER_LTO=y` | `-flto` |
| 去 C++ 开销 | 关 exceptions / RTTI | `-fno-exceptions -fno-rtti` | 同左 |
| 调试信息分离 | 输出 `.out`/`.map`，另存调试产物 | `CONFIG_APP_BUILD_TYPE_ELF_RAM` / 分离 `.elf` 与烧写镜像 | `-g0` 或用 `objcopy --strip-debug` |

> **平台差异提示**：ESP32 系（Xtensa / RISC-V）的体积里含有大量 ROM 中已有的库函数
> 与 WiFi/BT 协议栈，跟裸机 MCU 不可直接类比；此时看"应用自身增量"比看总量更有意义。

## 二、代码层

- **查重复实现**：同一个功能被多份拷贝实现（每个模块各抄一份环形缓冲、各写一份 CRC）
  是体积大户。先合并，再谈优化。
- **`printf` 家族是重灾区**：
  - 只在调试用的日志，用宏在发布版本里整段编译掉，而不是运行时判断。
  - 需要浮点的 `printf` 会拖进整套浮点格式化代码；不需要就不要链接浮点支持。
  - 能用轻量整数输出（自写 hex/dec 输出）就不要上 `printf`。
- **`switch`/查表 vs 计算**：两者是**双向**的。小范围枚举用查表更省（无重算逻辑）；
  大表且能算出结果时，算法更省。**要用 `.map` 数据判断方向**，别凭直觉。
- **去掉未使用的抽象层**：为"通用性"引入的函数指针表、虚函数、驱动注册框架，
  在只支持一种外设的产品里全是纯开销。
- **内联与去内联都要试**：`-Os` 下编译器已倾向不内联；手动 `always_inline` 在多个调用点
  会复制代码。对只被调用一次的小函数可以手动内联；被多处调用的大函数反之。
- **错误路径的处理文本**：长断言字符串、文件路径、`__FILE__` 会显著占 Flash。
  发布版本考虑去掉或改成错误码。

## 三、数据层

- **漏 `const` 的常量表会吃掉 RAM**。查找表、字模、初始化数组一律加 `const`，
  让它进 Flash 而不是 RAM（对 RAM 紧张的 MCU 这一项常能救回几百字节到几 KB）。
- **大数组换表示法**：
  - 字模、编码表可用压缩（行程编码 / 列式存储）后运行时解压；
  - 定点数表可改小数据类型（`uint32` → `uint16`，前提是精度够）；
  - 稀疏表改用分段 / 计算插值。
- **字符串**：界面文本、协议名字符串、错误描述占用的量常被低估。
  多语言或长文本考虑外置到独立 Flash 区或按需加载。
- **避开浮点**：浮点常量与库例程会连带拖入大量代码；能用定点就不上浮点。
- **栈与堆的裁剪**：确认启动文件里的栈大小是否远超实测需求；堆（heap）如果没用到动态分配，
  直接设成 0，否则链接器会预留。

## 四、验证与余量

- **每次改动后重测 ROM 与 RAM**，并记录到项目文档，形成体积账本。
- **保留 ≥20% 余量**（即用量不超过预算的 80%）。理由很实际：后续修 bug、加兼容性分支
  都会吃掉体积，恰好卡满的固件在下一个需求就得推倒重来。
- **功能回归必须做**：体积优化的典型副作用是
  LTO 暴露了原本被掩盖的重名符号、`gc-sections` 回收了"看起来没人用其实靠链接顺序生效"的段、
  MicroLIB 改了库函数行为。**优化后必须跑完整功能测试**，不能只看编译通过。
- **诚实汇报**：区分"由 `.map` 直接读出的数字"（实测）与"按经验预估的收益"（推断）。
  报告里不要写"预计可省 2KB"这种没验证的数字。

## 五、优化速查顺序（按性价比）

1. 确认不是 `-O0` 或带 `-g` 的调试配置 → 改 `-Os`
2. 打开函数/数据分段 + 段回收
3. 换精简 C 库（MicroLIB / newlib-nano）
4. 查重复实现与未使用抽象层（**这一项经常比编译选项收益更大**）
5. 检查漏 `const` 的大常量表
6. 精简 `printf` 与错误字符串
7. 试 LTO（必须复测，可能变大）
8. 大表压缩 / 换数据类型
