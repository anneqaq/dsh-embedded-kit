# 嵌入式调试方法论

## 一、第一原则：先缩小范围，再谈原因

**最常见的错误是"边猜边改"** —— 改一个地方、烧一次、看现象，运气好蒙对，运气差引入新问题。
正确顺序是**先把范围砍半**，只在最小范围里找原因。

按性价比排序的定位手段：

| 手段 | 砍掉的假设 | 代价 |
|---|---|---|
| **断开/旁路外部器件** | "是外部问题还是 MCU 问题" → 直接砍一半 | 需要能断开 |
| **只保留单通路**（只留一个通信口/一个任务/一个中断） | 并发与抢占相关 | 要能裁剪功能 |
| **二分注释代码**（注掉后半段看现象是否还在） | 代码位置 | 快，但要注意注掉后时序变了 |
| **换一块板 / 换一颗芯片** | "是硬件个体问题还是设计问题" | 需要备件 |
| **降速/降频** | 时序余量、建立时间相关问题 | 会掩盖真实工况 |
| **看数据找规律**（统计出现时的温度/电压/负载） | 环境相关性 | 需要记录 |

## 二、测量：不要用 printf 测时序

`printf` 本身耗时（一个字符几十 µs 到几百 µs），**它会改变你正在测量的东西**。
测时序必须上硬件手段：

| 目的 | 手段 | 要点 |
|---|---|---|
| 函数进出/ISR 耗时 | **GPIO 翻转 + 逻辑分析仪/示波器** | 用空闲引脚，翻转两条指令，开销几十 ns 级；比 printf 可靠得多 |
| 精确周期数 | **DWT->CYCCNT**（Cortex-M3+） | 开 `DEMCR.TRCENA` + `DWT->CTRL.CYCCNTENA`；M0/M0+ **没有 DWT** |
| 中断响应延迟 | GPIO 在 ISR 入口翻转 + 触发源同时抓 | 能直接量出从事件到 ISR 第一条指令的时间 |
| 通信时序 | 逻辑分析仪抓 **DE 脚 + 总线 A/B** 同时 | 判断方向切换裕量只有这一条可靠（见 `protocol-review`） |
| 电流/功耗 | 专用电流表或串已知电阻测压差 | 万用表 µA 档的内阻会改变电路；调试器连着测不准 |

**GPIO 翻转是最被低估的工具**：一个空闲引脚 + 一台便宜逻辑分析仪，能解决大量"时序对不对"的问题。

## 三、日志：设计而不是事后加

- **分级**：`ERROR`（必须处理）/ `WARN`（可疑）/ `INFO`（状态迁移）/ `DEBUG`（细节）。
  发布版本把 DEBUG 整段编译掉（用宏），不是运行时判断 —— 那既省体积也省时间。
- **要能事后看**：串口日志在掉电/复位后就没了。关键状态要落到**可持久读取**的地方
  （备份寄存器、NVM、环形日志区），否则偶发故障永远抓不到。
- **日志本身不能是瓶颈**：
  - 不要在 ISR 里 `printf`（阻塞 + 重入）。
  - 高频事件用**计数**替代打印（"CRC 错 N 次、超时 M 次"），比逐条打印有效得多。
  - 用环形缓冲把格式化工作挪到主循环。
- **每条日志要能定位**：带模块/行号/关键变量值。"通信失败"这种日志等于没打。

## 四、可调试性设计（在写代码时就做）

1. **状态可查询**：状态机的当前状态、各任务的进度、错误计数器，留一个只读接口。
2. **错误分类计数**：不要只用一个"错误标志"。超时、CRC 错、无响应要**分开计数** ——
   它们的根因完全不同，混在一起现场无法定位。
3. **保留符号表**：发布 hex/bin 的同时**留一份对应的 ELF**。没有符号表，PC 翻译不了。
4. **一个空闲 GPIO + 一个空闲串口**，专门留给调试。
5. **复位标志要在启动时读取并保存**，否则下次上电证据就没了（见 `fault-diagnosis`）。

## 五、故障注入：主动把问题逼出来

偶发问题的正确做法不是"等它出现"，而是**主动制造触发条件**：

- **边界注入**：把缓冲区喂到刚好满/溢出、把队列喂满、把计数器推到最大值。
- **时序扰动**：在最敏感的临界区前后插入随机延迟，放大竞态窗口。
- **异常注入**：通信上故意发错帧/超时/断线；电源上做慢上电与掉电。
- **压力注入**：把主频/波特率提到极限，让余量不足的问题暴露。
- **长跑**：连续跑 24~72 小时（内存泄漏、计数器回绕、温度漂移都靠这个）。

这些要**在调试阶段做**，别指望在现场发现。

## 六、断点：类型与限制（很多"灵异现象"来自断点本身）

| 断点类型 | 数量 | 影响 |
|---|---|---|
| 硬件断点 | 通常 4~6 个（受 FPB 限制） | 不停 CPU，可用于中断与 Flash 代码 |
| 软件断点 | 数量多 | **要改写指令** → 不能用于 Flash 中的代码（除非器件支持） |
| 数据观察点 | 2~4 个 | 能抓"谁改了这个变量"，**排查野指针/越界的利器** |

- **断点会改变时序**：停在断点期间，通信超时、看门狗、DMA 都继续跑（或已被暂停导致从机超时），
  于是"一断点就正常/一断点就出错"。**不要用断点验证时序。**
- 排查"变量被莫名改写"：用**数据观察点**，比读代码猜快得多。
- 低功耗相关的调试：调试逻辑本身耗电，**连着调试器测出的功耗是错的**。

## 七、"改了就没了"怎么办

现象改动后就消失，是最难的类别。原因是**你改的东西改变了时序/内存布局**，而不是修掉了根因。

处理办法：
1. **不要因为"改好了"就收工** —— 记录下你改了什么，以及它改变了什么（时序？栈用量？地址？）。
2. **查内存布局敏感性**：加一个无关变量现象就变 → 强烈提示**越界写/野指针**，
   去查那个被踩的地址附近有什么。
3. **查时序敏感性**：加一条指令现象就变 → 提示**竞态或建立时间不足**，用 GPIO 翻转 + 逻辑分析仪量。
4. **用压力与故障注入把它放大到必现**，再定位。

## 八、排查顺序清单

1. 有**复位标志/故障现场**吗？先读出来，不要先猜。
2. 能**稳定复现**吗？不能就先做故障注入或长跑把它变成必现。
3. 用二分法把范围**砍到最小**（断开外部、只留单通路）。
4. 是**时序问题**还是**逻辑问题**？时序必须用硬件测量，不要用 printf 或断点。
5. 是否**内存相关**（越界/栈溢出/未初始化）？查数据观察点与栈水位。
6. 是否**并发相关**？看共享变量、临界区、ISR 与主线的交互。
7. 每次只改**一处**并复测；改了现象就变时，记录"改了什么"而不只是"好了"。
